# Share-Ed Load Test

โปรเจกต์นี้ใช้ **k6**, **GitHub Actions** และ **Discord** เพื่อตรวจสอบความเร็วและความเสถียรของเว็บไซต์ Share-Ed แบบอัตโนมัติ โดยออกแบบให้เน้นการอ่านข้อมูล จึงไม่สร้าง แก้ไข หรือลบข้อมูลจริง

## ระบบนี้ทำงานอย่างไร

Push โค้ด หรือกด Run workflow → GitHub Actions เปิดเครื่องทดสอบชั่วคราว → Docker รัน k6 → วัดเวลาและความผิดพลาด → เก็บผลลัพธ์ → ส่งสรุปเข้า Discord

หากค่า Threshold ไม่ผ่าน งานจะขึ้นสีแดงเพื่อเตือนให้ตรวจสอบ ไม่ได้แปลว่า GitHub Actions เสีย

## ก่อนเริ่มทดสอบ

1. กำหนดขอบเขตให้ชัด: ชุดทดสอบนี้ใช้เฉพาะการอ่านข้อมูล และไม่ควรรันกับข้อมูลสำคัญโดยไม่จำเป็น
2. เริ่มจากผู้ใช้จำลองน้อย ๆ ก่อน เพื่อได้ค่าอ้างอิงของระบบ
3. สำหรับการทดสอบหลังล็อกอิน ต้องมีบัญชีทดสอบแยก และตั้ง GitHub Secrets ให้ครบ
4. จดผลของ profile เดิมไว้ทุกครั้ง เพื่อเปรียบเทียบก่อนและหลังปรับปรุงได้อย่างถูกต้อง

## ชุดทดสอบที่มี

| เลือกใน Workflow | ไฟล์ | ใช้ตรวจอะไร | เมื่อควรใช้ |
| --- | --- | --- | --- |
| smoke | smoke-test.js | ผู้ใช้ 1 คน 3 รอบ: Home, รายการโพสต์, หมวดหมู่ และ Profile | ใช้หลังแก้โค้ดทุกครั้ง |
| authenticated | authenticated-smoke.js | Login → ข้อมูลผู้ใช้ปัจจุบัน → รายการโพสต์ → รายละเอียดโพสต์ | ใช้ยืนยันเส้นทางของผู้ใช้ที่ล็อกอินแล้ว |
| diagnostic | diagnostic-test.js | ผู้ใช้ 1 คน 5 รอบ และแยกเวลา p95 ของแต่ละ API | ใช้หาว่า endpoint ใดช้า |
| load20 | load-test.js | เพิ่มผู้ใช้จำลองขึ้นไปถึง 20 VUs | ใช้ตรวจโหลดปกติก่อนนำเสนอ |
| capacity | capacity-test.js | เพิ่มได้ 20, 50 หรือ 100 VUs ตามค่าที่เลือก | ใช้ประเมินขีดความสามารถแบบค่อยเป็นค่อยไป |

**VU (Virtual User)** คือผู้ใช้จำลอง 1 คน ไม่ใช่บัญชีผู้ใช้จริง 1 บัญชี

## ลำดับที่แนะนำ

1. รัน **smoke** หลังแก้โค้ด เพื่อเช็กหน้าและ API สาธารณะอย่างรวดเร็ว
2. รัน **authenticated** ที่ 1 VU เพื่อเช็กว่า Login และสิทธิ์ผู้ใช้ยังทำงานจริง
3. รัน **diagnostic** เพื่อแยกให้เห็นว่า Home, Posts, Profile หรือ API ใดช้า
4. รัน **load20** เมื่อสองขั้นแรกผ่าน เพื่อจำลองผู้ใช้พร้อมกันสูงสุด 20 คน
5. รัน **capacity** ที่ 20 → 50 → 100 VUs ตามลำดับ เฉพาะเมื่อระดับก่อนหน้าผ่านและระบบพร้อม

หยุดเพิ่มโหลดและตรวจสอบก่อน ถ้า Request ล้มเหลวตั้งแต่ 1% หรือ p95 เกิน 1,000 ms อย่างต่อเนื่อง

## ข้อมูลที่ต้องมีสำหรับการทดสอบหลังล็อกอิน

ตั้งค่าที่ GitHub repository: **Settings → Secrets and variables → Actions**

| Secret | ใช้ทำอะไร |
| --- | --- |
| TEST_EMAIL | อีเมลของบัญชีทดสอบ |
| TEST_PASSWORD | รหัสผ่านของบัญชีทดสอบ |
| SUPABASE_ANON_KEY | ให้ k6 ขอ session จาก Supabase ได้ |
| DISCORD_WEBHOOK_URL | ส่งสรุปผลไปยังช่อง Discord |

ห้ามใส่ค่า Secret ลงในไฟล์ JavaScript, README, commit หรือ Discord ข้อมูลบัญชีทดสอบที่ใช้ควรไม่มีข้อมูลส่วนตัว และสคริปต์ authenticated ทำเฉพาะการอ่านข้อมูล

## แต่ละขั้นตอนใน Workflow ทำอะไรบ้าง

1. **ดาวน์โหลดไฟล์จาก repository** — ใช้ script และ workflow เวอร์ชันล่าสุด
2. **เตรียมโฟลเดอร์ผลลัพธ์** — สร้างโฟลเดอร์ results สำหรับ JSON และสรุป
3. **รัน k6 ตามชุดที่เลือก** — เลือกไฟล์จากค่า TEST_PROFILE
4. **สรุปผลภาษาไทย** — อ่านผลดิบของ k6 แล้วแสดง Request, error rate, p95 และ Checks
5. **สร้างข้อความสำหรับ Discord** — แปลงผลให้เป็นข้อความอ่านง่าย พร้อมลิงก์ไปยัง Action run
6. **ส่งรายงานเข้า Discord** — ทำเฉพาะเมื่อมี Secret DISCORD_WEBHOOK_URL
7. **เก็บผลเป็น Artifact** — ดาวน์โหลดผลละเอียดจากหน้า Action ภายใน 30 วัน
8. **จบงานตามผล k6** — หาก Threshold ไม่ผ่าน งานจะ fail เพื่อให้เห็นปัญหาชัดเจน

## วิธีรันจาก GitHub

1. เปิดแท็บ **Actions** ของ repository
2. เลือก workflow **Share-Ed Load Test**
3. กด **Run workflow**
4. เลือก smoke, authenticated, diagnostic, load20 หรือ capacity
5. หากเลือก capacity ให้เลือกจำนวนสูงสุด 20, 50 หรือ 100 VUs
6. เปิดงานที่รันเสร็จเพื่อดู Console, ขั้นตอนส่ง Discord และ Artifact

การ commit ไฟล์ JavaScript หรือ workflow จะสั่ง smoke test อัตโนมัติ เพื่อเตือนปัญหาเร็วขึ้น ส่วนการแก้ README อย่างเดียวจะไม่เริ่มทดสอบ

## วิธีรันบนเครื่องตัวเองด้วย Command Prompt

1. เปิด Command Prompt
2. พิมพ์ cd /d D:\LoadTestEye
3. พิมพ์คำสั่งนี้

    docker run --rm -v "%cd%:/work" -w /work grafana/k6:1.7.1 run smoke-test.js

เปลี่ยน smoke-test.js เป็น diagnostic-test.js, load-test.js หรือ capacity-test.js ได้ตามต้องการ สำหรับ authenticated แนะนำให้รันจาก GitHub Actions เพื่อเก็บข้อมูลรับรองไว้ใน Secrets

## อ่านผลอย่างไร

| ค่า | ดีเมื่อ | ความหมาย |
| --- | --- | --- |
| VUs | ตรงกับจำนวนที่เลือก | จำนวนผู้ใช้จำลองที่ทำงานพร้อมกันสูงสุด |
| http_req_failed | น้อยกว่า 1% | สัดส่วน Request ที่ล้มเหลว |
| http_req_duration p95 | น้อยกว่า 1,000 ms | 95 ใน 100 Request ตอบกลับภายใน 1 วินาที |
| Checks | ผ่านทั้งหมด | เงื่อนไขสำคัญ เช่น status และข้อมูลที่คาดหวัง ถูกต้อง |
| http_reqs | เปรียบเทียบใน profile เดียวกัน | จำนวน Request และอัตรา Request ต่อวินาที |

เช็กว่า “ไวขึ้น” โดยเทียบ **p95 และ error rate ของ profile เดิม ภายใต้จำนวน VUs เดิม** ไม่ควรเทียบเพียงค่าเฉลี่ยหรือการรันครั้งเดียว เพราะเครือข่ายและ cold start อาจทำให้ผลแกว่งได้

## ดูผลลัพธ์ได้ที่ไหน

- **GitHub Actions Console**: ดูผลทันทีและดูว่าขั้นตอนใด fail
- **Discord**: ดูสรุปภาษาไทยแบบรวดเร็ว
- **Artifact**: ดาวน์โหลด JSON และไฟล์ผลละเอียดไว้เปรียบเทียบย้อนหลัง

ถ้า workflow เป็นสีแดง แต่ Checks ผ่านและ error rate เป็น 0% มักหมายถึงระบบยังทำงานได้ แต่ค่า p95 เกิน Threshold จึงควรเปิด diagnostic เพื่อหาว่า API ใดเป็นสาเหตุ

## สถานะที่ควรติดตามก่อนนำเสนอ

- Smoke ผ่าน เพื่อยืนยันหน้าและ API หลัก
- Authenticated ผ่าน เพื่อยืนยัน Login และ session ของบัญชีทดสอบ
- Diagnostic ชี้จุดช้าได้ชัดเจน
- Load20 ผ่าน Threshold อย่างน้อย 2–3 รอบในช่วงเวลาต่างกัน
- จึงค่อยเพิ่ม Capacity เป็น 50 และ 100 VUs หากต้องรองรับผู้ใช้พร้อมกันระดับนั้น

## ความปลอดภัย

สคริปต์ทั้งหมดใน repository นี้ไม่ควรสร้าง แก้ไข หรือลบโพสต์ ผู้ใช้ หรือข้อมูลอื่น หากจะเพิ่ม flow ที่เปลี่ยนข้อมูล ต้องใช้บัญชีและข้อมูลทดสอบที่แยกจาก production และขออนุมัติก่อนเสมอ
